Payment Service: an architecture walkthrough

Covers how the QuickEats payment microservice is structured, which architectural styles and patterns it uses and why, how it keeps money consistent across services, and the trade-offs you should be ready to defend. Every claim points to the actual code in quickeats-backend/services/payment.

At a glance

The payment service is one of five Go microservices (identity, catalog, order, payment, notification). It owns everything about money: the customer's saved card, charging an order, refunding it, and keeping an accounting ledger.

Place in the system

QuickEats follows a microservices architecture with database-per-service, an API gateway (Kong), and event-driven communication through Kafka.

Internal architecture: hexagonal (ports & adapters)

Inside, the service follows Hexagonal Architecture (also described as Clean Architecture). The business core sits in the middle and knows nothing about HTTP, PostgreSQL or Kafka. Infrastructure plugs into it through interfaces called ports.

SOLID link to mention The ports are the Dependency Inversion Principle: the high-level use case depends on the abstraction port.CardRepository, and the low-level postgres.CardRepo also depends on (implements) it. The use cases taking interfaces in their constructors is constructor dependency injection, done by hand in main.go.

Benefits you can claim (with evidence)

  • Testability: domain/card_test.go and app/ledger_test.go test card validation and the ledger maths without a database. CardUseCase even injects now func() time.Time so expiry logic is deterministic.
  • Modifiability: swapping PostgreSQL or adding a real payment gateway only touches the adapter layer.
  • Separation of concerns: HTTP status codes live only in router.go (paymentError maps domain declines to 422). The use case never mentions HTTP.

Design patterns used

Strategy pattern (GoF, behavioural)

The algorithm for "how do I charge this payment method" is behind an interface, chosen at runtime by name.

// domain/strategy.go  — the Strategy interface
type PaymentStrategy interface {
    Execute(ctx context.Context, payment *Payment) (*PaymentResult, error)
}

// cmd/server/main.go — registering concrete strategies
strategies := map[string]domain.PaymentStrategy{
    "card": gateway.NewCardStrategy(cardRepo),
}

// app/create_payment.go — the Context selects one at runtime
strategy, ok := uc.strategies[req.Method]
result, err := strategy.Execute(ctx, payment)
  • Roles: Strategy = PaymentStrategy; ConcreteStrategy = CardStrategy; Context = CreatePaymentUseCase.
  • Open/Closed Principle: adding PayPal or a real card gateway means a new struct plus one map entry. Execute doesn't change.
  • Built for asynchronous gateways too: PaymentResult.Completed=false with a GatewayRedirectURL models a gateway that confirms later (for example a hosted checkout page with a webhook).
  • History: the project used to have a wallet method. Migration 002_cards_replace_wallets replaced it, and the strategy design is what made that change local.

Repository pattern

PaymentRepository, LedgerRepository and CardRepository present collection-like access to aggregates and hide the SQL. Use cases work with *domain.Payment, never with rows.

Transactional Outbox (microservice pattern)

The service must change its database and tell Kafka. Doing both directly would be a dual write: if the process crashes between them, the two disagree. Instead, the event is inserted into an outbox table in a DB transaction (outbox.WriteToOutbox). A background Relay polls every 2 s, publishes, and marks rows published_at.

  • Gives at-least-once delivery. Consumers de-duplicate by EventID (events.Deduplicate with Redis) and also check business state.
  • FOR UPDATE SKIP LOCKED lets several replicas run relays without publishing the same row twice, so the service can scale horizontally.

Saga participant (orchestration)

Placing an order spans order, catalog and payment, each with its own DB, so a single ACID transaction is impossible. The order service is the saga orchestrator (order/internal/app/saga.go). Payment is a participant that offers an action (charge) and its compensating action (refund).

Saga stepActionCompensation
1. CatalogReserve stockRelease stock
2. PaymentCharge card (/internal/payments/intent)Refund (/internal/payments/refund)
3. OrderConfirm order, commit stockCancel order (plus the above)

Runtime flows

A. Placing and paying for an order (happy path)

B. Declined payment

  1. CardStrategy.Execute returns ErrNoCard or ErrInsufficientFunds.
  2. domain.FailureReason maps it to a code: no_card, insufficient_funds or payment_failed.
  3. The payment is marked FAILED (reason stored in gateway_ref) and a payment.payment.failed event is written to the outbox.
  4. The HTTP response is 422 with error.details.reason. The order service reads it as PaymentDeclinedError.
  5. The saga compensates: cancels the order with that reason and releases stock. The app can tell the customer exactly what to fix.
Two signals, one outcome The order gets both the 422 and the failed event. That's safe because compensation is idempotent: the second attempt sees the order is already cancelled and does nothing.

C. Refund (compensating transaction)

Triggered when an order is cancelled or rejected after payment, or when a payment completes for an order that was already cancelled (e.g. a timeout race). RefundToCard runs one DB transaction:

UPDATE payments SET status='REFUNDED' WHERE id=$2 AND status='COMPLETED' RETURNING amount;
UPDATE cards SET balance = balance + amount WHERE user_id = $userId;
COMMIT;   -- then reverse ledger entries are written

The AND status='COMPLETED' guard makes refunds idempotent: a second call matches no row and returns refunded:false, so money can never be returned twice.

D. Managing a card (customer-facing)

PUT /api/v1/cards/me → JWT auth → CardUseCase.AddCard → domain.NewCard validates (13–19 digits, Luhn checksum, holder name, expiry not past, CVV 3–4 digits) → CardRepo.Save upserts (one card per user, ON CONFLICT (user_id)). Validation errors become a 400 with the failing field so the UI can highlight it.

Double-entry ledger with commission split

Payment of 45,000 cents (LKR 450.00):
  DEBIT   customer:<id>        45,000   order payment
  CREDIT  shop:<shopId>        42,750   order revenue (95%)
  CREDIT  platform:revenue      2,250   platform commission (5%)
                               ------
  Σ debits == Σ credits == 45,000      ← invariant tested in ledger_test.go

The platform share is computed as amount − shopShare rather than amount × 5%, so rounding remainders are never lost (test case: 33,333 cents still balances).

Money is stored as int64 minor units (cents) Never floats. This avoids binary rounding errors (0.1 + 0.2 ≠ 0.3). Schema uses BIGINT, and CHECK (balance >= 0) is a last-line database guard.

Data management & consistency

This is the section examiners probe most for a payment service. Know these five mechanisms.

1. Idempotency: one payment per order

Execute first looks up GetByOrderID. If a payment exists it returns the original outcome (or the original decline) instead of charging again. The DB backs this with order_id UUID UNIQUE. Why it matters: Kafka redelivery or saga retries can call intent more than once, and a customer must never be charged twice.

2. Atomic, race-free debit

UPDATE cards SET balance = balance - $1
WHERE user_id = $2 AND balance >= $1      -- check and change in ONE statement

Avoids the check-then-act race (TOCTOU). Two simultaneous orders can't both pass a separate "is there enough?" check and overdraw the card. If zero rows change, a follow-up query tells "no card" from "insufficient funds". This is effectively optimistic concurrency at row level. The earlier CheckCard call is only a UX pre-check; the debit is the real guard.

3. Eventual consistency across services

Payment and order data live in different databases, so they are only eventually consistent: for up to ~2 s (relay interval) a payment can be COMPLETED while its order is still PENDING_PAYMENT. That's the CAP / BASE trade-off: we keep each service available and independent instead of using distributed transactions (2PC), which would couple them and hurt availability.

4. Transactional outbox + at-least-once + de-duplication

Events are never lost (stored in the DB first) but may be delivered twice. Consumers handle that in two layers: events.Deduplicate by EventID in Redis, plus business-state guards (order status checks).

5. Compensation instead of rollback

Refund is the semantic undo of a charge, done in its own local transaction. It's idempotent and safe to call for orders that were never charged.

Schema evolution

Versioned up/down migrations run by a dedicated payment-migrate container before the service starts:

  • 001 creates payments, ledger_entries, wallets, outbox (with a partial index on unpublished rows).
  • 002 replaces wallets with cards (business change: card payments).
  • 003 adds shop_id so ledger credits go to the shop. It fixed a bug where entries were posted to the order ID, and TestPaymentEntriesCreditTheShopNotTheOrder is the regression test for it.

Deployment view

  • Container: multi-stage build (golang:1.22-alpine → alpine:3.19). CGO_ENABLED=0 static binary; final image has no compiler, so it's smaller with less attack surface.
  • Startup ordering (compose depends_on conditions): payment-db healthy → payment-migrate done → payment-seed done → payment starts (also waits for Kafka and Redis).
  • Configuration: 12-factor style environment variables via pkg/config (DATABASE_URL, KAFKA_BROKERS, JWT_SECRET, PORT).
  • CI/CD (Jenkinsfile): Checkout → Build & test (go build / vet / test) → Docker build (tag = git SHA) → Push to ECR → Deploy (deploy/deploy.sh) → Health check, with rollback to the previous tag on failure.
  • Infrastructure: single AWS EC2 instance (eu-north-1) running Docker Compose. Kong is the only public port (80). Databases and services stay on the private Docker network.
Be honest about the deployment trade-off All containers run on one EC2 host, so the host is a single point of failure. It's a cost decision for a student project. The service design (stateless, own DB, outbox with SKIP LOCKED) is ready for ECS/Kubernetes with multiple replicas and RDS without code changes.

Likely viva questions

Try to answer out loud before opening each one.

Why is payment a separate microservice and not part of the order service?

Different bounded context and reason to change: money rules, card data and accounting vs. order lifecycle. Separating them gives fault isolation, its own database (sensitive financial data isolated), independent deployment and scaling, and a smaller security scope. A future real gateway integration is also contained here.

What architectural style does the service use internally? Explain the layers.

Hexagonal / ports & adapters. domain holds entities and rules; port defines interfaces the core needs; app holds use cases; adapter implements HTTP, Postgres and the card gateway; main.go is the composition root. Dependencies point inward (Dependency Rule / DIP).

Where is the Strategy pattern and what does it buy you?

domain.PaymentStrategy is the interface, gateway.CardStrategy the concrete strategy, and CreatePaymentUseCase the context that picks one from a map by req.Method. New payment methods are added without modifying the use case (Open/Closed). It made the wallet-to-card change local, and PaymentResult.Completed/GatewayRedirectURL already supports redirect-style gateways.

How do you guarantee a customer is never charged twice?

Three layers: (1) Execute checks for an existing payment for the order and returns its outcome; (2) payments.order_id is UNIQUE so a second row can't exist; (3) consumers de-duplicate events and the saga checks order status before acting. Refund uses WHERE status='COMPLETED' so it can't refund twice either.

Two orders are placed at the same moment with a balance that covers only one. What happens?

Both may pass the pre-check, but the debit is one conditional statement, UPDATE … WHERE balance >= amount. Postgres row locking serialises them: one succeeds, the other affects zero rows and gets insufficient_funds, so its order is cancelled. The CHECK (balance >= 0) constraint is a final safety net.

What is the transactional outbox and why not just publish to Kafka directly?

Publishing directly after a DB commit is a dual write: a crash between the two loses the event (or publishes an event for a change that rolled back). Writing the event into an outbox table in the same DB transaction makes it durable; a relay publishes it later. Result: at-least-once delivery, handled with idempotent consumers. (Be ready to admit that completePayment currently uses a separate transaction for the outbox row, and the fix is one transaction.)

How does the system stay consistent without distributed transactions?

An orchestrated saga in the order service. Each step is a local transaction with a compensating action: reserve stock / release; charge / refund; confirm / cancel. Consistency is eventual (seconds), which we accept for availability and loose coupling instead of 2PC.

Why does the order service call payment synchronously but listen for events too?

The sync call gives an immediate decline reason so the order can be cancelled with a precise message. The event announces the fact for any consumer and drives order confirmation, and it would also support gateways that complete later. Duplicated signals are safe because handlers are idempotent.

How is card data protected?

Only display data (brand, last4, holder, expiry) is stored; the full number and CVV are validated then discarded (data minimisation in the spirit of PCI-DSS). Card routes need a JWT and act only on the caller's own user ID from the token, never a user ID in the URL. The balance never leaves the service. Internal endpoints aren't exposed through Kong, and port 8084 isn't published in production.

Why a double-entry ledger? Isn't the payments table enough?

The payments table records state; the ledger records money movement per account (customer, shop, platform) as an append-only audit trail. Debits must equal credits, which is an invariant you can verify. It supports the 95/5 commission split and shop payouts, and refunds are reversing entries rather than deletes.

Why are amounts int64 and not float/decimal?

Floating point can't represent most decimal fractions exactly, causing rounding drift. Integer minor units (cents) are exact and fast. The commission is amount*95/100, with the platform taking the remainder so totals always balance.

How would you scale the payment service?

It's stateless, so run more replicas behind the internal load balancer. The relay is replica-safe via FOR UPDATE SKIP LOCKED. Scale the DB vertically or with read replicas for card reads. Kafka partitions keyed by order allow parallel consumers. Next steps: managed Postgres (RDS), container orchestration (ECS/K8s) with health-check-based restarts.

What happens if the payment service is down when an order is placed?

The card pre-check fails, so the order handler logs a warning and still places the order (graceful degradation). When the saga calls intent it gets an error, treats it as payment_failed, and compensates (cancels and releases stock). No money is taken, and the customer sees a cancelled order. A retry/circuit-breaker would improve this.

How would you add a real payment gateway like Stripe?

Write StripeStrategy implementing PaymentStrategy: create a payment intent at Stripe and return Completed=false plus a redirect/client secret. Register it under "stripe" in main.go. Add a webhook adapter (inbound) that verifies the signature and calls a CompletePayment use case, which writes status + ledger + outbox. Domain, other strategies and the order service stay unchanged.

How is the service tested?

Unit tests at the domain/app layer: table-driven card validation tests, brand detection, failure-reason mapping, and ledger invariants (balance, reversal, credit goes to shop not order). Time is injected for deterministic expiry tests. Jenkins runs go vet and go test before building images. Gap to mention: no integration tests against a real Postgres; testcontainers would be the next step.

Which ADRs (architecture decisions) would you document for this service?

(1) Database per service. (2) Hexagonal internal structure. (3) Strategy for payment methods. (4) Transactional outbox for events. (5) Orchestrated saga with refund as compensation. (6) Integer minor units for money. (7) Store only card display data. Each with context, decision, consequences.

Final revision

60-second pitch

"The payment service is an independent Go microservice with its own PostgreSQL database. Internally it follows hexagonal architecture: a pure domain layer, use cases, ports, and adapters for HTTP, Postgres and the card gateway, wired in main.go. Payment methods use the Strategy pattern, so new gateways plug in without touching the use case. In the order saga it's a participant: it charges the card through an idempotent internal endpoint with an atomic conditional debit, records a balanced 95/5 double-entry ledger, and publishes completed or failed events through a transactional outbox to Kafka. If the order is cancelled, refund is the compensating transaction, which is also idempotent. Card numbers and CVVs are never stored, and the balance never leaves the service."
